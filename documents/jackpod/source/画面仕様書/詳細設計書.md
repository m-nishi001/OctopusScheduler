# 詳細設計書 — 管理画面（Admin）

対象: 管理画面に含まれるすべてのサブ画面（景品管理・メンバー管理・アセット管理・画面設定・抽選演出設定）

前提（重要）

- この設計は local-first を原則とする。アプリは起動時に `index.html` を取得した後、UI 表示と編集操作は原則ローカル（IndexedDB / localStorage）で完結する。GAS への通信はローカルに保存されたデータを Google Drive または Spreadsheet と同期する場合のみ行う（セカンドストレージ）。

注意: 実行画面側の Vue コンポーネントは既に存在するため、可能な限り既存コンポーネントを参照・再利用する。実行画面用のコンポーネント API（props/events）を管理画面側で呼び出すのではなく、設定データ（JSON）を保存して実行側がそれを読み込む方式を採る。

この設計書は画面ごとのUI要素、データ検証、API呼び出しシーケンス、IndexedDBとの同期方法、UIワイヤー（要素配置）を具体的に定義する。

## 2. 画面別詳細

### 2.1 景品管理（Prizes）

目的: 景品の追加・編集・並び替え・在庫管理を行う。設計上、景品の在庫（quantity）は常に 1 に固定される。

主要操作

- 一覧表示: サムネイル、名前、ランク、在庫、表示順、編集/削除ボタン
- 追加ボタン: `+ 追加` を押すと編集モーダルを開く
- 編集モーダル: 入力項目を編集し保存
- ドラッグで並び替え: order を更新

入力項目（PrizeEdit モーダル）
| フィールド | 型 | 必須 | バリデーション | UI要素 |
|---|---:|:---:|---|---|
| name | string | Yes | 1-100 文字 | テキスト入力 |
| rank | number | Yes | 1-100 | 数値入力（select推奨） |
| description | string | No | max 2000 | リッチテキスト（HTML）|
| imageAssetId | string | No | asset存在チェック | AssetPicker（単数）|
| bgmAssetId | string | No | asset存在チェック | AssetPicker（単数）|
| seAssetIds | string[] | No | each asset exists | AssetPicker（複数）|
| order | number | Yes | 0..9999 | 自動/手動編集 |
| quantity | number | Yes | 1（固定） | UI上は表示のみ or 編集不可（固定値） |

バリデーションルール

- name: 空不可
- rank: 整数, 1以上
- quantity: 常に 1（UI上は編集不可とする）
- ファイルサイズ: image <= 5MB, audio <= 20MB, video <= 50MB

保存シーケンス

1. クライアントは入力内容をローカルで検証
2. IndexedDB に暫定保存（optimistic, temporary id 付与）
3. 背景で /api/prizes に POST（または PUT）を呼ぶ
4. サーバーが成功するとサーバー発行の id を返却
5. クライアントは IndexedDB の暫定 id を正規 id に更新

API 例
POST /api/prizes
Request:

```
{ "prize": { "id": "p_..." (optional), "name": "...", "rank": 1, "quantity": 3, ... } }
```

Response:

```
{ "prize": { ... } }
```

アップロード仕様（実装参照と処理の流れ）

- 本プロジェクトでは localForage を使った LocalStorageService が既に実装済みです。参考ファイル:
  - `src/client/packages/common-lib/src/storage/local-storage-service.ts`（LocalStorageService: localforage ラッパー）
  - `src/client/octopus-scheduler/src/model/infrastructures/assets/asset-repository.ts`（AssetRepository: LocalStorageService を使い、GAS同期ロジックを実装）

- 処理の流れ（クライアント）
  1. ユーザーがファイルをアップロード／ドロップする
  2. フロントでファイルを Blob のまま `LocalStorageService.save(id, asset)` に保存する（即時プレビューはこのローカルデータを参照）。
  3. UI は `LocalStorageService.getAll()` で一覧を取得してプレビュー表示する。
  4. 同期トリガ（手動の「同期」ボタン、または定期バッチ）で `AssetRepository.syncAssets(onProgress?)` を呼ぶ。
  5. `syncAssets` は `GasFunctionService` 経由で GAS 関数（例: `getDriveMetaData`, `addDriveData`, `updateDriveData`）を呼び、差分に基づき Drive へ upload/update を行う。

- AssetRepository の主要メソッド（参考実装）:
  - `addAssets(assets: Asset[]): Promise<string[]>`
  - `getAssets(): Promise<Asset[]>`
  - `getAssetById(id: string): Promise<Asset | null>`
  - `deleteAssets(ids: string[]): Promise<void>`
  - `syncAssets(onProgress?: (msg: string) => void): Promise<void>`

API 例（GAS 側は同期用の関数を提供）

- GAS 関数例: `addDriveData(driveData)`, `updateDriveData(driveData)`, `getDriveMetaData(folderId)`
- 既存実装ではこれらを `GasFunctionService.call(...)` で呼んでいます。

データ保持

- LocalStorageService（localForage）にはメタデータ（id, type, name, url, uploadedAt, blob, lastUpdated 等）を保存します。UI はローカルの blob を使って即時プレビューを行います。
- 同期中は進捗を AssetRepository.syncAssets の onProgress コールバックで通知します。
  | attributes | string[] | No | - | タグ入力（複数） |
  | order | number | Yes | 0..9999 | 自動/手動 |

保存シーケンス: Prizes と同様（IndexedDB→API同期）

バリデーション

- name 必須
- photo ファイルサイズ上限 5MB

【QA】

- メンバーの一意キーは現在 `id`（内部発行）とする。name は表示用のみでユニーク性は強制しない。外部IDやメールでの一意化が必要な場合は後続で拡張可能。

### 2.3 アセット管理（Assets）

目的: 画像/音声/動画/HTML等のアップロード管理と参照

機能

- 一覧（フィルタ: type、検索: name）
- アップロード（ドラッグ＆ドロップ / ファイル選択）
- プレビュー（画像は即時表示、音声は試聴、動画は再生）
- 選択（AssetPicker で他画面へ割当）
- 削除（注意: 削除前に使用箇所の存在チェック推奨）

アップロード仕様

- クライアントはファイルを選択後、IndexedDB に一時保存（base64 or blob 参照）
- 背景で /api/asset に送信（multipart/form-data）
- サーバーは Drive に保存し assetId, url を返す

API 例
POST /api/asset
Request: multipart/form-data (file, metadata)
Response:

```
{ "assetId": "asset_...", "url": "https://drive..." }
```

データ保持

- IndexedDB にはメタデータ（id, type, name, url, uploadedAt）を保存。
- アップロード中は progress を UI に表示。

削除ポリシー

- 管理画面で削除を許可するが、実行設定がそのアセットを参照している場合は警告を出す。運用ルールで定期クリーンを推奨。

【実装方針】

- アップロード後の Drive 共有設定は運用に合わせて切替可能とします。デフォルトは署名付きURL（短期）を推奨しますが、単一ユーザー運用で利便性を優先する場合は公開リンクをデフォルトにしても構いません。管理画面に共有設定フラグを設けて切替可能にしてください。

### 2.4 画面設定（Screens）

目的: 各実行画面の要素配置・表示順・BGM/SE/演出設定を行う

構成

- 画面タイプ選択（home/opening/description/demo/main/result）
- 要素一覧（elements）: 並び替え、追加、編集
- 要素編集: type 別の設定（text: content, font, size / image: assetId, size / video: assetId, loop）
- 演出設定: animationSettings（type, duration, delay, params）
- BGM/SE 割当: AssetPicker で選択

保存シーケンス: IndexedDB に保存→API 同期

JSON 例（opening screen）

```
{
  "id":"screen_opening",
  "type":"opening",
  "bgmAssetId":"asset_bgm_opening",
  "elements":[
    { "id":"el1","type":"text","content":"ようこそ！","order":0, "settings":{ "animation":"scroll","duration":12000 }},
    { "id":"el2","type":"image","assetId":"asset_img_logo","order":1 }
  ]
}
```

バリデーション

- elements は order が連続する int（0..N）
- 指定 assetId の存在チェック

【QA】

- カスタム HTML を許可する場合は XSS 対策を必須とする。実装方針としては、管理画面側で入力をサニタイズ（許可タグを限定）して保存し、実行側でもサニタイズ済みの HTML のみをレンダリングする。可能ならばカスタム HTML は最小限に留め、代わりにテンプレート要素（text/image/embed）で表現することを推奨。

### 2.5 抽選演出設定（LotterySettings）

目的: ルーレットやスロットなどの演出アルゴリズムとパラメータを定義

主要パラメータ

- method: roulette|slot|random
- duration: ms
- easing: linear|easeInOut|power2
- particle: boolean
- speedCurve: array<number>

JSON 例

```
{
  "id":"lottery_settings",
  "method":"roulette",
  "params":{ "duration": 8000, "easing":"power2.inOut", "spinCount":6 }
}
```

## 3. IndexedDB スキーマ（クライアント）

- objectStores
  - prizes (keyPath: id)
  - members (keyPath: id)
  - assets (keyPath: id)
  - screenConfigs (keyPath: id)
  - lotterySettings (keyPath: id)
  - pendingSync (keyPath: tempId) // 同期待ちキュー

各ストアの最小スキーマは基本設計を参照。

重要: local-first 設計に合わせ、IndexedDB が一次ソースとなる。GAS は同期先（secondary）であり、保存用 API 呼び出しは UI 操作の同期ボタンや定期バックグラウンド同期で行う。

同期ロジック（詳細）

- pendingSync に write 操作を push
- backgroundSyncWorker がキューを順次処理
- 成功すると pendingSync から該当エントリを削除し、該当ストアを正規データで上書き

競合と排他（単純化）

- 本設計では景品在庫が常に 1 固定のため、複雑な在庫デクリメント処理は不要。実行時の抽選ではローカルのデータを参照して当該景品が既に消費済みかを判定し、消費処理はローカルで行う。サーバー同期時に差分として反映するが、厳密な分散トランザクションは想定しない（GAS はバックアップ/同期先）。

## 5. UI イベントとシーケンス（主要シナリオ）

シナリオA: 景品編集

1. 管理画面で `編集` を押す
2. PrizeEdit モーダルが開く（IndexedDB からデータロード）
3. ユーザーが修正して `保存` を押す
4. クライアントで検証→IndexedDBに暫定保存→pendingSync キューに登録→UIに「保存中」表示
5. 背景で API 呼び出し→成功で IndexedDB のデータを更新、トーストで成功表示

シナリオB: アセットアップロード

1. Asset 管理でファイルを選択
2. アップロード中は進捗バーを表示
3. サーバー返却の assetId を受け取ったら assets ストアに追加
4. 必要に応じて既存の screenConfig/prize/member の assetId を置換

## 6. バリデーションとエラー処理

- クライアント: 各フィールドの即時検証。エラーはフィールド横に表示。IndexedDB に保存する際は最小限の検証（必須/型/サイズ）を行う。
- サーバー(GAS): サーバーは secondary storage として最小限の検証（構造検証、権限簡易チェック）を行う。ビジネスロジック（抽選アルゴリズムの整合）はクライアントが一次担当する。
- 通信失敗: pendingSync に残り、UI に再試行ボタンを表示。同期は手動トリガまたは定期同期（例: アプリ起動時とユーザーの同期ボタン）で行う。

## 7. セキュリティ

- 管理画面は軽量な認証/チェックを行えば可（運用で OAuth を導入する選択肢は残す）。GAS は public にしないこと、かつ同期 API 呼び出しに対しては簡易なリクエスト元チェックを行う。
- アップロードファイルは MIME チェックとサイズチェックを行う（クライアントでサイズチェック、サーバーでも再チェック）。
  -- 指示に基づき、本プロジェクトは単一ユーザー利用を前提とするため、厳密な XSS 対策やサニタイズは必須としません。管理者（単一利用者）が自由に HTML を入力・保存・表示できる運用を許容します。
  - 注意: 将来的に複数ユーザーや公開運用に移行する場合は、`DOMPurify` 等の導入を推奨します。

## 8. 実装ガイドライン（シンプルでテストしやすい設計）

- クラス設計方針
  - 単一責務（SRP）を厳守する。例: PrizeRepository, MemberRepository, AssetService, SyncService, ScreenConfigService。
  - リポジトリ層は IndexedDB を直接扱い、インターフェース（TypeScript）で抽象化しておく。GAS同期は SyncService に集約する。
  - サービスは副作用を最小化し、戻り値で結果を返す（副作用は呼び出し側で行う）。これによりユニットテストが容易になる。

- Vue コンポーネント方針
  - UI は小さく再利用可能なコンポーネントに分割する（FormField, AssetPicker, EntityList, ConfirmModal, Toast）。
  - 各コンポーネントは明確な props / emits を持ち、外部状態は親コンポーネントで保持する。
  - 実行画面の既存 Vue コンポーネントは参照し、設定JSONの形状に合わせて props 名を整理する。管理画面から実行画面のコンポーネントを直接呼ぶのではなく、共通の types とデータスキーマを共有する。
