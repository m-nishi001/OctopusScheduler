# セッション基盤(ホスト / 管理 / 参加者)

会場の投影端末・運営の手元の端末・参加者のスマホを、**セッション(パーティールーム)**で結ぶ仕組みの設計と運用メモです。実装は `packages/session-hub`、画面は `apps/app-scheduler` の `/sessions` `/session/host/:id` `/session/console/:id` `/portal`。

## 1. 端末の役割

| 役割 | 誰が | 何をする |
| --- | --- | --- |
| **ホスト** | プロジェクターにつないだ会場のPC(管理者ログイン必須) | 演出画面を表示し、管理端末の指示を実行し、いまの状態を公開する(状態の権威) |
| **管理** | 運営の手元の端末(管理者ログイン必須) | 画面切り替え・「次へ」・受付の締切などをコマンドとして送る。ホストの在席や回答数を見る |
| **参加者** | 来場者のスマホ(ログイン不要) | 参加コード/QRでポータルに入り、状態を見て、ホストが許可した入力だけを送る |

セッションは管理者が `/sessions` で作成します。どの端末から開いても同じ一覧が見えます。参加コードは進行中のセッション間で重複しません。

## 2. データの流れ

```
管理 ──コマンド(seq採番・重複排除)──▶ セッション ──push/poll──▶ ホスト(順に1回ずつ適用 → ack)
参加者 ──許可された入力/回答──────────▶            ◀── 状態(RoomState)を公開 ──┘
管理・参加者 ◀── 状態・在席・回答数(参加者には運営向けの情報を渡さない)
```

- **コマンド**: 追記型。`seq` で順序を保証し、`requestId` で再送を重複排除する。ホストは適用済み `seq` を保存し、リロードしても二重適用しない。リロード中に古くなったコマンド(既定30秒超)は適用しない。
- **状態(RoomState)**: ホストが名前空間ごと(`session` / `jackpot` / `quiz`)に公開。参加者に見せてよい情報だけにする(当選者は停止演出の後、正解は正解発表の後)。
- **ホスト遷移の許可リスト**: 管理端末がホストに開かせてよい画面は `isAllowedHostPath` で制限(管理画面や外部URLは不可)。信頼境界はホスト側。
- **回答ラウンド**: クイズなどの一斉回答。締切は**サーバ時刻**で強制され、ホストのタブが落ちても自動で終わる。先着で1人1回。回答は1件ごとに全員へ配信せず、回答数だけをまとめて運営端末へ届ける。

## 3. 実行基盤の違い

| | GAS | Cloudflare |
| --- | --- | --- |
| 更新の受け取り | ポーリング(サーバが `nextPollMs` で間隔を指示) | WebSocket(Durable Object が push)。繋がらなければ低頻度ポーリングへ自動切替 |
| 排他 | ScriptLock | Durable Object の直列実行(ロック不要) |
| 想定人数 | **約30人**(同時実行・書き込みクォータ) | **数百人** |
| 保存 | KV(1値 ~9KB 以内。回答は100件まで) | DO ストレージ(回答はメモリに溜めて alarm でまとめて保存) |

### Cloudflare 無料枠の予算

Workers 10万リクエスト/日、DO 書き込み10万行/日などの無料枠に対し、**想定最大(参加者300人・2時間のイベントを1日2回・全員一斉の再接続3回・20問)でも30%以内**に収めることを、テスト(`packages/session-hub/src/server/room/__tests__/quota-budget.spec.ts`)で固定しています。直近の試算は リクエスト約9.4千/日(9%)、DO書き込み約3.2千行/日(3%)。上限値と出典は `packages/session-hub/src/shared/quota-budget.ts`。

守るべき設計上のルール:

- 更新は push。ポーリングで数百人を捌かない(参加者300人×3秒間隔だと約17分で枠を使い切る)。
- 参加者の入力は WebSocket(20件=1リクエスト換算)。回答はコマンドのリングに載せない。
- ハートビートは書き込まない(在席は間引く)。

### GAS のデプロイ設定

`appsscript.json` の `webapp.access` が `MYSELF` のままだと、参加者(別アカウントのスマホ)がポータルを開けません。参加者が使う運用では、デプロイ時に「アクセスできるユーザー」を適切に設定してください(誰でも / Google アカウントを持つ全員など)。この変更はデプロイ担当者の判断事項として、リポジトリの既定値は変更していません。

## 4. アカウントと復帰

- 本番モード(`app-mode.config.json` = `production`)では、セッション作成・ホスト/管理への入室は管理者ログイン必須。参加者はログイン不要(参加コードが入口)。最初の管理者の登録手順は README を参照。
- 端末ごとの入室情報(`sessionId` / `deviceId` / token)はブラウザに保存し、誤リロードや再読み込みで自動復帰する。ホストは適用済み `seq` も保存する。
- ホストは1セッションに1台。別端末が引き継ぐと(確認あり)、旧ホストは `replaced` になりコマンドを受け付けない。

## 5. 画面とエンドポイント

- `/sessions`(一覧・作成・終了)、`/session/host/:id`(ホスト起動・QR・データ取り込み)、`/session/console/:id`(ホストの在席/未適用件数、画面切替、ジャックポット/クイズ操作、操作ログ)、`/portal/:code?`(参加)。
- RPC: `sessionHub_*`(作成/一覧/終了/運営者入室/参加者入室/poll/コマンド発行/状態公開/回答ラウンド4種)。契約は `packages/session-hub/src/server/session-hub-api-contract.ts`。

## 7. 新しいゲーム/機能をつなぐには

1. ホスト側の画面で `HostAgent` の `router.register("<名前空間>", handler)` を登録し、`publishSlice("<名前空間>", state)` で状態を公開する(画面を離れたら `clearSlice`)。ジャックポットは `use-jackpot-host.ts`、クイズは `use-quiz-host.ts` が実例。
2. 参加者の入力が必要なら、ホストが許可したコマンド種別(`clientInput`)で受ける。一斉回答は回答ラウンドを使う。
3. 管理コンソールに操作パネルを足し、`connection.issue("<名前空間>", "<種別>")` を送る。
4. 遷移先の画面は `isAllowedHostPath`(`packages/session-hub/src/shared/host-navigation.ts`)の許可リストに追加する。
5. 参加者に見せる情報は公開する状態に含めるものだけにする(答えを先に渡さない)。
