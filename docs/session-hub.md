# セッション基盤(ホスト / 管理 / 参加者)

> **要点**
> - 会場の投影 PC（ホスト）・運営の手元の端末（管理）・参加者のスマホを、**セッション**で結ぶ
> - ホスト／管理／参加者のすべてがログイン必須。参加者は受付のQR（またはID/パスワード）でログインして入る
> - 更新は Cloudflare では WebSocket（数百人）、GAS ではポーリング（約 30 人）
> - 新しいゲームをつなぐ手順は [§7](#7-新しいゲーム機能をつなぐには)

会場の投影端末・運営の手元の端末・参加者のスマホを、**セッション(パーティールーム)**で結ぶ仕組みの設計と運用メモです。実装は `packages/session-hub`、画面は `apps/app-scheduler` の `/sessions` `/session/host/:id` `/session/console/:id` `/portal` と、ログイン済み参加者向けの `packages/participant-portal`（`/p`）。デプロイは [GAS](deploy-gas.md) / [Cloudflare](deploy-cloudflare.md)、全体の構成は [architecture.md](architecture.md) を参照してください。

## 1. 端末の役割

| 役割 | 誰が | 何をする |
| --- | --- | --- |
| **ホスト** | プロジェクターにつないだ会場のPC(管理者ログイン必須) | 演出画面を表示し、管理端末の指示を実行し、いまの状態を公開する(状態の権威) |
| **管理** | 運営の手元の端末(管理者ログイン必須) | 画面切り替え・「次へ」・受付の締切などをコマンドとして送る。ホストの在席や回答数を見る |
| **参加者** | 来場者のスマホ(参加者アカウントでログインする) | 受付QRでログインしてポータルに入り、状態を見て、ホストが許可した入力だけを送る |

セッションは管理者が `/sessions` で作成します。どの端末から開いても同じ一覧が見えます。

## 2. データの流れ

```
管理 ──コマンド(seq採番・重複排除)──▶ セッション ──push/poll──▶ ホスト(順に1回ずつ適用 → ack)
参加者 ──許可された入力/回答──────────▶            ◀── 状態(RoomState)を公開 ──┘
管理・参加者 ◀── 状態・在席・回答数(参加者には運営向けの情報を渡さない)
```

- **コマンド**: 追記型。`seq` で順序を保証し、`requestId` で再送を重複排除する。ホストは適用済み `seq` を保存し、リロードしても二重適用しない。リロード中に古くなったコマンド(既定30秒超)は適用しない。
- **状態(RoomState)**: ホストが名前空間ごと(`session` / `jackpot` / `quiz`)に公開。参加者に見せてよい情報だけにする(当選者は停止演出の後、正解は正解発表の後)。
- **ホスト遷移の許可リスト**: 管理端末がホストに開かせてよい画面は `isAllowedHostPath` で制限(管理画面や外部URLは不可)。信頼境界はホスト側。
- **回答ラウンド**: クイズなどの一斉回答。締切は**サーバ時刻**で強制され、ホストのタブが落ちても自動で終わる。先着で1人1回。回答は1件ごとに全員へ配信せず、回答数だけをまとめて運営端末へ届ける。

## 3. 実行基盤の違い

| | GAS | Cloudflare |
| --- | --- | --- |
| 更新の受け取り | ポーリング(サーバが `nextPollMs` で間隔を指示) | WebSocket(Durable Object が push)。繋がらなければ低頻度ポーリングへ自動切替 |
| 排他 | ScriptLock | Durable Object の直列実行(ロック不要) |
| 想定人数 | **約30人**(同時実行・書き込みクォータ) | **数百人** |
| 保存 | KV(1値 ~9KB 以内。回答は100件まで) | DO ストレージ(回答はメモリに溜めて alarm でまとめて保存) |

### Cloudflare 無料枠の予算

Workers 10万リクエスト/日、DO 書き込み10万行/日などの無料枠に対し、**想定最大(参加者300人・2時間のイベントを1日2回・全員一斉の再接続3回・20問)でも30%以内**に収めることを、テスト(`packages/session-hub/src/server/room/__tests__/quota-budget.spec.ts`)で固定しています。直近の試算は リクエスト約9.4千/日(9%)、DO書き込み約3.2千行/日(3%)。上限値と出典は `packages/session-hub/src/shared/quota-budget.ts`。

守るべき設計上のルール:

- 更新は push。ポーリングで数百人を捌かない(参加者300人×3秒間隔だと約17分で枠を使い切る)。
- 参加者の入力は WebSocket(20件=1リクエスト換算)。回答はコマンドのリングに載せない。
- ハートビートは書き込まない(在席は間引く)。

GAS で参加者に使ってもらう場合のデプロイ設定は [deploy-gas.md](deploy-gas.md#参加者に使ってもらう場合) を参照してください。

## 4. アカウントと復帰

- アプリ全体がログイン必須(公開はログイン画面のみ)。参加者アカウントは受付QRまたはID/パスワードでログインし、`/p` に入る。詳細と初回管理者の作り方は [authentication.md](authentication.md) を参照。
- 端末ごとの入室情報(`sessionId` / `deviceId` / token)はブラウザに保存し、誤リロードや再読み込みで自動復帰する。ホストは適用済み `seq` も保存する。
- ホストは1セッションに1台。別端末が引き継ぐと(確認あり)、旧ホストは `replaced` になりコマンドを受け付けない。

## 5. 画面とエンドポイント

- `/sessions`(一覧・作成・終了・**参加者ポータルへの公開**)、`/session/host/:id`(ホスト起動・ログイン案内・データ取り込み)、`/session/console/:id`(ホストの在席/未適用件数、画面切替、**イベントの開始/終了**、ジャックポット/クイズ操作、操作ログ)、`/p`(ログイン済み参加者のポータル)。
- 会場の画面（ホストが開く）: `/event-entry`（エントリー受付のバブル）。ホストが開いてよい画面の許可リストに入っている。
- RPC: `sessionHub_*`(作成/一覧/終了/運営者入室/参加者入室/**ポータル公開の指定・ポータル入室**/poll/コマンド発行/状態公開/回答ラウンド4種)。契約は `packages/session-hub/src/server/session-hub-api-contract.ts`。

## 5.5 参加者ポータル(ログイン済みの参加者)

受付QR（[authentication.md](authentication.md#参加者の受付qr)）でログインした参加者は、管理者が「ポータルに公開」したセッションに自動で入ります（参加コードを入れる入室は無く、サーバーも受け付けません）。

**運営の流れ**

1. `/sessions` でセッションを作り、ホスト端末で `/session/host/:id` を開く
2. 一覧の「ポータルに公開」を押す（公開は同時に1つ。別のセッションを公開すると前のは外れる。終了すると外れる）
3. 参加者は受付でQRを読み取る → `/p` に着地し、公開中のセッションに入る
4. 管理コンソールの「参加者ポータルのイベント」にイベント名を入れて「イベントを開始」→ **全員の画面の上に「イベント発生中!」が固定表示**される。タップするとイベント画面へ。「イベントを終了」で消える
5. 途中参加の人も、入った時点でイベント発生中なら最初からバナーが出る

**クイズ・ジャックポット（ポータルのホーム）**

参加者ポータルのホームに、進行中のものが**上から順に**出る（何も無いときだけ「いまイベントは行われていません」）。

| 表示 | 内容 |
| --- | --- |
| 参加者の操作 | ホストが受け付けている操作のボタン（例: 「ルーレットを止める」）。押すとホストへコマンドとして届き、受付が終わると消える |
| クイズ | 出題（問題・色つきの選択肢・残り時間）→ 回答 → 正解発表（正解と正誤）→ 結果発表中。回答は先着で1人1回（**別の端末でも**。2台目で押すと元の選択を表示）。回答済みはメンバーごとに保存し、リロードしても残る |
| ジャックポット | 当選者・賞品は、**ホストの停止演出が終わってから**公開される（先にネタバレしない） |
| バナー | 回答受付中でまだ答えていないクイズがあると「クイズ出題中!」を画面上部に固定表示（ホームへ）。クイズが無ければ、従来のイベント / エントリー受付のバナー |

- ポータルはゲームのパッケージに依存せず、公開された状態（`quiz` / `jackpot` / `clientInput`）を**形を検証して読む**。形が合わないものは「無い」として扱う。公開する側との形の一致は、アプリの契約テスト（`portal-state-contract.spec.ts`）で確かめている

**エントリー受付**（イベントの中で参加者を募る。ジャックポットの抽選対象などに使う）

1. 管理コンソールの「エントリー受付を開始」→ 参加者の画面に **「エントリー受付中!」** と大きな「エントリー」ボタンが出る（バナーも「エントリー受付中!」に変わる）
2. 「エントリー受付(バブル)」（または「会場の画面にエントリーを映す」）で、会場の画面が `/event-entry` に切り替わる。**エントリーするたびに、顔写真つきのバブルがポンと現れ**、人数が増える。コンソールにも新しい順の一覧と人数が出る
3. 「エントリーを締め切る」で受付終了（エントリー済みの人には「結果をお待ちください」）。**「エントリー受付を再開」で、エントリー済みの人を残したまま途中参加を受け付け直せる**
4. 「イベントを終了」で、受付中なら締め切って、すべての表示を消す

| 項目 | 内容 |
| --- | --- |
| 受付の実体 | 回答ラウンド（オープン型）。運営が締め切るまで開き続け、選択肢は「エントリー」1つ。ラウンドはセッションに1つだけなので、**同じセッションでクイズの回答受付を始めるとエントリーの一覧は置き換わる**（抽選の対象は、受付を締めたあとにホストが取り込んでおく想定） |
| 1人1回 | ログインから確定したメンバーは、**別の端末（2台目のスマホ）からでも1件**。参加者は全員ログイン済みで、メンバーIDはクライアントの申告ではなくトークンから決まる |
| 顔写真 | ホスト端末が持つジャックポットのメンバー写真から引く（`MemberPhotoCache`）。参加者のスマホには写真を渡さない。写真が無い人は名前の頭文字のアバター |
| 抽選への反映 | 下記「ジャックポットの抽選の対象」。名簿の識別子はアカウントのIDで、ジャックポットのメンバーと同じ |
| 参加者の「済み」 | メンバーごとにブラウザへ保存（1台のスマホを何人かで使っても取り違えない）。別の端末で済みの人が押しても「済み」と返る |

**ジャックポットの抽選の対象（エントリーした人だけ）**

- エントリー受付を**最初に開始すると、ジャックポットの抽選の対象が自動で「エントリーした人だけ」になる**。管理コンソールの「ジャックポットの抽選の対象」で「全メンバー」に切り替えたり、戻したりできる（切り替えた設定は、受付を再開しても上書きしない）
- 抽選（メンバー抽選のリールに流れるダミーも含む）は、**対象の中の、まだ当選していない人**から選ぶ。対象の全員が当選済み・対象が0人のときは、理由を表示して抽選を止める
- 対象は抽選のたびに**回答ラウンドから最新を取得**する（受付中のままでも反映される）。締め切ったときの一覧はホスト端末に保存し、のちに同じセッションでクイズなど別の回答受付が始まってラウンドが置き換わっても、保存した一覧で抽選できる
- **一覧を取得できないときは、全メンバーにフォールバックしない**（対象外の人が当選する事故を防ぐ）。保存した一覧があればそれを使い、無ければエラーにして、通信を確認してもう一度試してもらう
- 実装の境界: ジャックポットは `DrawPoolProvider`（`@octopus/game-jackpot`）という口だけを持ち、アプリのホストが `setDrawPoolProvider` で「エントリーした人」の実装を渡す。ジャックポットは session-hub を知らない

**エントリーが殺到しても無料枠を守る仕組み**

- 参加者のエントリーは WebSocket の1メッセージ。回答は1件ごとには配信せず、**回答数だけを2秒ごとにまとめて**運営端末へ届ける
- 会場の画面とコンソールは、**回答数が変わったときだけ**エントリー一覧を取りに行く。取得は**最短1.5秒間隔**にまとめ、失敗しても自動では再試行しない
- イベントの状態（受付中/終了）にはエントリー数を含めない（エントリーのたびに全員へ配信しないため）

**仕組み**

| 項目 | 内容 |
| --- | --- |
| 入室 | `sessionHub_joinPortal`（ログイン済みなら誰でも）。メンバーIDと表示名は**サーバーがログインのトークンから決める**（クライアントの申告は受け取らない） |
| 復帰 | リロードしても同じ端末として復帰する。**別のメンバーが同じ端末でログインしたら、前の人の端末には復帰せず新しい端末になる**（共有端末対策）。ログアウトで保存した入室情報も消す |
| イベント | 管理端末が `event.start { title }` / `event.end` を送り、ホストが `event` 名前空間の状態として公開する。型と検証は `packages/session-hub/src/shared/portal-event.ts`。ホストをリロードしても、端末に保存してあるイベントを公開し直す |
| 公開の指定 | 一覧のインデックスの `portal` フラグだけを書き換える（Durable Object は触らない） |

**無料枠への配慮**（暴走の防止）

- 参加者は WebSocket の push だけで更新を受け取り、**定期的な問い合わせはしない**。公開中のセッションが無いときも、タイマーでは再確認しない
- 切断・終了・認証切れのあとの**自動の入り直しは最大3回**。入室できてもすぐ切れる状態でも無限には繰り返さない。回数を数え直すのは**30秒以上つながり続けたあと**だけ。上限後は「つなぎ直す」ボタンに任せる
- 画面に戻ったときの再試行は、前回の試行から5秒以上あけ、つながっていないときだけ
- 公開中のセッションを別のものに切り替えても、すでに接続中の参加者は元のセッションに残る（新しく入る人から切り替わる）。全員を移したいときは、元のセッションを終了する


**結果(クイズの順位・ジャックポットの当選履歴)**

参加者ポータルの「結果」タブ(`/p/results`)に、クイズの順位・総合ランキング・自分の正誤、ジャックポットの当選履歴(自分の当選は強調)を出す。

| 項目 | 内容 |
| --- | --- |
| 保存先 | **R2(GAS は Google Drive の JSON)**にセッションごと1ファイル `results/json/<sessionId>.json`。Durable Object の状態(6KB 上限)には載せない |
| DO に載るもの | `results` 名前空間の `{ rev }` だけ(更新番号。数十バイト)。ホストが結果を保存するたびに公開する。ホストを再読み込みしても、保存済みの結果から rev を取り直して公開し直す |
| 書き込み | ホスト端末(管理者)。クイズは**順位発表の演出が終わってから** `putQuizResult`、ジャックポットは**当選者と賞品が画面に見えた後に** `putJackpotDraw`(どちらも演出の途中では保存しない=ネタバレ防止)。デモは保存しない。管理画面で結果をリセットするとホスト端末から `deleteJackpotDraw` で当選履歴も消す |
| 読み取り | `getResults`(ログイン済みなら誰でも)。サーバーが**本人向けに整形**して返し、他のメンバーのIDは含めない(順位表は上位10件、自分の順位・正誤、累計での自分の行) |
| 取り直し | rev が自分の取得済みより進んだとき、**「結果」を開いている間だけ**、最大3秒のばらつきを付けて取り直す。開いていなければタブに印(赤い点)を出すだけで通信しない。定期的な問い合わせはしない。失敗しても自動では再試行せず「再読み込み」に任せる |
| 累計の定義 | 正解1点。同点は正解の合計回答秒数が小さい順、それも同じなら名前順。メンバーIDが無い回答は対象外 |
| 上限 | 100ラウンド / 500抽選 / 1ラウンドあたり正解300件・不正解500件。超えると保存を拒否する |
| 冪等性 | ラウンドは `roundKey`、抽選は `drawId` で上書き。内容が変わらない再送では rev は進まない。ホストの再読み込みで回答が空になった書き直しが、保存済みの(回答の多い)結果を壊さない |
| 注意 | クイズの回答はラウンドごとに置き換わるので、**結果画面を表示せずに次のラウンドを始めると、その回の結果は残らない** |

## 6. テスト

共通のコマンドは [development.md](development.md#テストの種類) を参照。session-hub 固有の観点は次のとおりです。

| 観点 | 内容 |
| --- | --- |
| ユニット/コンポーネント | エンジン、DO中核、transport、各画面(連打・通信断・リロード・認証切れ・終了・不正パス) |
| 障害注入シミュレーション | 乱数シードで通信断・応答ロスト・重複を注入し、実行順の不変条件を確認 |
| 無料枠の予算 | 300人規模の負荷を再現して使用量を集計し、予算内であることを検証 |
| 実 workerd のスモーク | Durable Object / WebSocket / 回答ラウンドの通し(29項目) |
| 複数端末E2E | ホスト・管理・参加者を別コンテキストで同時に動かす通し(ジャックポット/クイズ含む) |

## 7. 新しいゲーム/機能をつなぐには

1. ホスト側の画面で `HostAgent` の `router.register("<名前空間>", handler)` を登録し、`publishSlice("<名前空間>", state)` で状態を公開する(画面を離れたら `clearSlice`)。ジャックポットは `use-jackpot-host.ts`、クイズは `use-quiz-host.ts` が実例。
2. 参加者の入力が必要なら、ホストが許可したコマンド種別(`clientInput`)で受ける。一斉回答は回答ラウンドを使う。
3. 管理コンソールに操作パネルを足し、`connection.issue("<名前空間>", "<種別>")` を送る。
4. 遷移先の画面は `isAllowedHostPath`(`packages/session-hub/src/shared/host-navigation.ts`)の許可リストに追加する。
5. 参加者に見せる情報は公開する状態に含めるものだけにする(答えを先に渡さない)。
