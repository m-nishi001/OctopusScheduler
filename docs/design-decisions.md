# 設計の意思決定と学び

> **要点**
> - GAS を最初に選んだのは、低コスト・Google アカウント基盤・現場で直せること
> - 規模が増えて TypeScript / Vue / clasp を導入し、その後 Cloudflare にも対応した
> - 型と構造のルールを強めにしたことで初速は上がったが、終盤は自由度を下げた
> - GAS の遅延と失敗は、リトライ・並列ダウンロード・ブラウザストレージで体感を改善した

## 1. なぜ最初に GAS か

運用コストを抑えられること、Google アカウント基盤によるセキュリティを活用できること、JavaScript ベースで Web エンジニアがキャッチアップしやすいことが理由です。本番中に不具合が出ても、開発 PC がなくても現場で直しやすい点も重視しました。

## 2. なぜ後から TypeScript + Vue + clasp か

機能が増えて、型のない実装では保守効率が急速に落ちたためです。開発環境の準備コストは増えましたが、品質と速度を保つうえでは妥当でした。特にテストで、GAS 単体では難しい検証を補えるようになりました。

## 3. 速度のための構造と、そのトレードオフ

短期間・単独開発で認知負荷を下げるため、型と構造のルールを強めにしました。変更影響の局所化と Open/Closed Principle の実践に効き、初期の速度が上がりました。一方で終盤は制約の強さが自由度を下げ、保守コストが増える場面もありました。

学び: 「初期段階での過度な一般化は避ける」「YAGNI とのバランスを常に見直す」。

## 4. GAS の制約下での性能改善

GAS 連携は時間帯によって関数呼び出しが失敗しやすいため、リトライ機構・並列ダウンロード・ブラウザストレージの活用を組み合わせて体感性能を改善しました。本番運用では、GAS 基盤としては大きな遅延を抑えられました。

## 5. 大人数のセッションは Cloudflare で

GAS のポーリングでは、同時実行と書き込みのクォータにより約 30 人が目安です。数百人規模を無料枠で動かすため、Cloudflare では Durable Object + WebSocket を採用しました。詳細は [session-hub.md](session-hub.md) を参照してください。

## 6. 認証は「入口で必須」「秘密は外に置く」

以前は、ビルド時の動作モードで認可を切り替えており、最初の管理者を作るのに 2 回のデプロイが必要で、戻し忘れると無認可のまま公開される危険がありました。そこで、動作モードを廃止して認可を常に有効にし、初回管理者はデプロイ物の外にあるシークレットで作る方式にしました。詳細は [authentication.md](authentication.md) を参照してください。

## 振り返り

機能を作るだけでなく、制約下での技術選定、品質と速度の両立、将来の保守性を見据えたトレードオフ判断の重要性を、実践を通して学びました。
