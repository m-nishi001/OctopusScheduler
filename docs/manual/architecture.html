OctopusScheduler のしくみ(図解)

アプリの構成と、管理者・参加者・サーバーがどうつながるかを、視点別の図で説明します。これから保守する人や、全体を知りたい人向けです。専門用語は最後の用語集にまとめています。

1. ひと目でわかる全体像

要点
  • 人が触るのは、管理者・会場ホストPC・操作端末・参加者スマホの4種類。どれも同じURLの1つのWebアプリを開く
  • アプリの裏側(サーバー)は GAS か Cloudflare のどちらか一方で動く。画面は同じ
  • データは、サーバー側の保存先に置かれる。保存先の種類は動かし方で違う

OctopusScheduler は、忘年会などでクイズ大会と抽選会を行うWebアプリです。インストールは不要で、ブラウザだけで動きます。下の図は、人・アプリ・サーバー・保存先が上から下につながる全体像です。

図の見方:角丸の枠=人・画面、太い枠=Webアプリ、二重線の枠=サーバー、円筒=保存先、青系=GAS・管理側、橙系=Cloudflare・参加者側(色が違っても枠の形と文字で区別できます)。

登場するもの意味
会場ホストPCプロジェクターにつないだPC。管理者でログインして、演出画面を映す
操作端末司会者の手元のスマホやPC。ボタンで進行を指示する
サーバーデータを預かり、画面からの依頼を処理する場所(GAS または Cloudflare)
保存先名簿・画像・設定などを実際にしまう場所

2. 2つの動かし方:GASとCloudflare

要点
  • 同じアプリを、GAS(Googleの無料サーバー)でもCloudflare(クラウド基盤)でも動かせる
  • 違うのは、配信・通信・リアルタイムの方法・保存先・想定人数
  • 参加者が約30人までなら GAS、数百人なら Cloudflare が目安
  • 画面とゲームの中身は共通。差は infrastructures だけに閉じている
項目GASCloudflare
配信(画面を届ける)HtmlService。doGet が1枚のHTMLを返すWorker が ASSETS(静的ファイル置き場)から配る
通信google.script.runPOST /rpc
リアルタイム(更新の受け取り)ポーリング(定期的に聞きに行く)。間隔はサーバーが nextPollMs で指示WebSocket(つなぎっぱなし)+Durable Object。失敗すると低頻度のポーリングに自動で切り替え
排他(同時書き込みの調整)ScriptLockD1 の locks と、Durable Object の直列実行
保存先スクリプトプロパティ・Drive・CacheServiceR2・D1・Durable Object
想定人数約30人数百人

ポイントどちらで動いているかは、アプリを使う人は気にしなくて構いません。デプロイの手順は deploy-gas.md と deploy-cloudflare.md にあります。

3. 役割と画面

要点
  • URLは1つ。ログインしたアカウントの役割(管理者か参加者)で、行き先の画面が決まる
  • 管理者は #/home、参加者は #/p に着地する
  • 会場ホストPCと操作端末は、どちらも管理者でログインして、セッションごとの画面を開く
  • 参加者が管理画面のURLを直接開いても、#/p に戻される
ルート(URLの # 以降)誰が使うか何をする画面か
#/login全員ログイン(受付QRもここに着地して自動でログイン)
#/home管理者設定・準備の入口
#/settings管理者メンバー・景品・クイズ・画面設定
#/session/host/:id会場ホストPC(管理者)セッションの演出画面。状態の正を持つ
#/session/console/:id操作端末(管理者)「次へ」などの指示を送る
#/p参加者エントリー・回答・結果の確認

:id はセッションごとに変わる番号です。入口のUXはブラウザ側の案内で、本当の防御はサーバー側の認可です(第5章)。

4. 通信のしくみ

要点
  • 画面とサーバーの会話は、型付きの呼び出し(RPC)で行う。名前は <prefix>_<name>
  • GAS と Cloudflare で入口は違うが、同じ名前の関数に届く
  • 各機能は secure("admin"|"public") で、誰が呼べるかを宣言する
  • npm run verify が、画面側の呼び出し名とサーバー側の関数が合っているかを突き合わせる

RPC は「遠くにある関数を、名前を指定して呼ぶ」しくみです。名前の前半(prefix)が機能の持ち主を表します。

グループ持ち主代表的な操作
accounts_*accountslogin・loginWithKey・listMembers・applyRoster・getSession
sessionHub_*session-hubcreateSession・joinOperator・poll・issueCommand・submitAnswer
quizGame_*game-quizgetRecord・saveRecord・putBlob・getBlob
jackpotGame_*game-jackpotgetRecord・saveRecord・addJson・getJson
octopusScheduler_*app-schedulerdoGet(画面配信)・getAssetBlob・saveAssetRecord

5. ログインと認証

要点
  • ログインは ID+パスワード、または受付のQR鍵。成功するとセッショントークン(有効7日)を受け取る
  • 以降の呼び出しは、サーバーが毎回トークンを検証する
  • 同じIDで5回連続失敗すると15分ロック。Cloudflareは、さらにIP単位のレート制限を持つ
  • 最初の管理者は、ブートストラップ用のシークレットで作る
  1. ブラウザが、ID+パスワードまたはQR鍵を送る。
  2. 入口が accounts 機能に認証を頼む。
  3. 失敗回数を保存先で確認する(5回連続の失敗で15分ロック。成功で戻る)。
  4. 合格なら、セッションを保存先に記録する(有効7日。1人10セッションまで。超えると古い順に失効)。
  5. accounts がトークンを入口へ渡す。
  6. 入口がトークンをブラウザに返す。ブラウザはそれを保存する(localStorage)。
  7. 以降は、トークンつきで呼ぶ。
  8. 入口が accounts にトークンの検証を頼む。
  9. accounts が保存先のセッションと照合する。
  10. OKなら処理を実行し、NGなら拒否して返す。
項目内容
エンドポイントの区分すべて secure("admin")(管理者のみ)か secure("public")(ログイン済みの誰でも。参加者向け)のどちらかを宣言する
セッションの期限7日。1人あたり最大10セッション
総当たり対策同じIDで5回連続失敗すると15分ロック。成功でリセット
Cloudflareの追加対策IP単位のレート制限(ログイン用60回/分、公開エンドポイント用1200回/分)。会場の共有IPでも弾かれない広さにしてある
初回管理者ブートストラップ用パスワード(シークレット)を登録し、ID admin でログインすると作られる。管理者が1人でもログインできれば無効になる

詳しくは authentication.md を参照してください。

6. 当日の進行(セッションハブ)

要点
  • ホスト(会場PC)が状態の正。操作端末はコマンドを送り、参加者は回答を送る
  • 3者はセッション(サーバー側のルーム)を介してつながり、直接は話さない
  • Cloudflareは WebSocket で即時に届け、GAS は定期的に聞きに行く(ポーリング)
  • 締切はサーバー時刻で決まるので、ホストのタブが落ちても自動で終わる
  1. 操作端末がコマンド(画面を進める等)を送る。番号(seq)で順序を保証し、再送は重複を捨てる。
  2. ホストがコマンドを順に1回ずつ適用する(リロード後も二重に適用しない)。
  3. ホストが、いまの状態を公開する。
  4. セッションが、状態・在席・回答数を操作端末と参加者へ配る(参加者には運営向けの情報を渡さない)。
  5. 参加者が、ホストが許可した回答だけを送る。
GASCloudflare
更新の受け取りポーリング(サーバーが nextPollMs で間隔を指示)WebSocket(Durable Object が押し出す)。失敗時は低頻度ポーリング
排他ScriptLockDurable Object の直列実行(ロック不要)
回答の保存値を25件ずつに分けて保存(100件まで)メモリに溜め、約2秒後にまとめて保存(alarm)
想定人数約30人数百人

設計の詳細と運用は session-hub.md にあります。

7. データの保存先マップ

要点
  • 保存するものを4種類(単純な値・ファイルとJSON・キャッシュと排他・セッションルーム)に分け、GASとCloudflareで置き場所を変える
  • 端末(ブラウザ)の IndexedDB がまず画面を出し、背景でsync-engineがサーバーと揃える
  • 同期は「新しい書き込みが勝つ」。通信待ちを画面に出さない
種類GASCloudflare
単純な値(名簿・設定)スクリプト プロパティR2(__scalars__/ の下)
ファイル・JSON(画像・音声・一覧)Drive(ルートフォルダ配下)R2
キャッシュ・排他CacheService・ScriptLockD1(cache_entries・locks)
セッションルームスクリプト プロパティ(KV)Durable Object(SESSION_ROOM)

ファイルと JSON は、環境を問わず <module>/<kind>/<name> のパスで指し、パスの組み立ては storage-paths.ts に集めてあります。一覧は種類ごとに { data, updatedAt } を1件持ち、更新日時の新しいほうが勝ちます。

注意2台でほぼ同時に別の項目を編集すると、あとから保存した一覧が残ります(一覧全体を1つの単位として同期するため)。

8. コードの構成(パッケージ地図)

要点
  • monorepo(1つのリポジトリに複数パッケージ)。本体は apps/app-scheduler の1つだけ
  • 機能(accounts・session-hub・participant-portal・game-jackpot・game-quiz)と、基盤(infrastructures ほか)に分ける
  • 他のパッケージの src/index.ts と /server だけを使う。内部パスには触れない
  • GAS/Cloudflareの違いは infrastructures の gas/container.ts と cloudflare/container.ts だけが知る
パッケージ役目
apps/app-scheduler画面の組み立てと、ルート・ログイン案内(本体)
accountsメンバー名簿・ログイン・セッション・認可
session-hubホスト/操作/参加者を結ぶセッション基盤
participant-portalログイン済み参加者向けのスマホ画面
game-jackpot / game-quizジャックポット抽選 / クイズ
infrastructuresGAS/Cloudflareの実装を差し替える層
sync-engine端末とサーバーの同期
client-common / composables / ui-kit共通サービス / 共通ロジック / 共通UI部品
table-ioCSV の読み書き

詳しくは architecture.md を参照してください。

9. ビルド・デプロイ・CIの流れ

要点
  • npm run build が各パッケージをビルドし、scripts/prepare-dist.js が dist/gas と dist/cloudflare にまとめる
  • npm run verify が、サーバー関数の契約と成果物を検査する
  • GAS は deploy:gas(clasp)、Cloudflare は deploy:cloudflare(wrangler)
  • GitHub Actions では、lint・unit・typecheck・build を並列に走らせ、最後に verify で集約する
コマンドやること
npm run build全パッケージをビルドして dist を作る
npm run verifyverify:gas(契約)+verify:dist(成果物)
npm run deploy:gasbuild して clasp push
npm run deploy:cloudflarebuild → setup:cloudflare → D1 のマイグレーション → wrangler deploy
npm run dev:stackローカルで丸ごと起動して確認する
npm run staging:up / staging:downCloudflareの検証環境を作る / 片付ける

手順は deploy-gas.md・deploy-cloudflare.md・development.md を参照してください。

10. 用語集と関連ドキュメント

要点知らない言葉に出会ったらここへ。詳しい説明は下の関連ドキュメントへ進んでください。

GAS(Google Apps Script)
Googleのアカウントで動かせる無料のサーバー環境。
Cloudflare Workers
Cloudflareが提供する、小さなプログラムを動かす基盤。このアプリでは /rpc と /ws/<sessionId> を受け持つ。
R2 / D1 / Durable Object
Cloudflareの保存先。R2=ファイル置き場、D1=小さなデータベース、Durable Object=セッションごとに1つ持つ「部屋」(状態を覚えて、WebSocketを受ける)。
RPC
遠くの関数を名前で呼ぶしくみ。このアプリでは <prefix>_<name> の形。
ポーリング / WebSocket
ポーリング=一定間隔で聞きに行く。WebSocket=つなぎっぱなしで、変化があったらすぐ届く。
セッション
2つの意味がある。ログインの有効期間(トークン)と、当日の進行の「部屋」(セッションハブ)。
ホスト / 操作端末
ホスト=会場の投影PC(状態の正)。操作端末=司会の手元(コマンドを送る)。
IndexedDB
ブラウザの中にある保存場所。まず手元から表示し、背景でサーバーと揃える。
sync-engine
端末とサーバーを「新しい書き込みが勝つ」で揃える部品。
ブートストラップ
最初の管理者を作るための、一時的なシークレット(パスワード)。
monorepo / turbo
複数パッケージを1つのリポジトリで管理する形 / そのビルドを効率よく回す道具。
clasp / wrangler
GAS / Cloudflare にデプロイするコマンドラインの道具。
e2e
実際の画面を自動で操作して、通しで動くか確かめるテスト。
