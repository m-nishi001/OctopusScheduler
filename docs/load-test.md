# 負荷テスト(参加者50人 + 運営2人 + ホスト)

本番と同じ順にイベントを最後まで通し、**参加者50人と運営が同時に接続した状態で、Cloudflare(Worker / Durable Object / R2 / D1)が正しく動き続ける**ことを確かめる。
特に「クイズの回答が同時に集中したとき」「選び直しが連打されたとき」の DO と R2 の挙動を見る。

2つのテストがある。どちらも同じ `BASE` に対して動き、ローカル(wrangler dev --local)でも staging でも実行できる。

| テスト | 中身 | 時間 |
|---|---|---|
| `load`(protocol版) | 参加者50 + 管理2 + ホストをすべて合成し、実際のクライアントと同じ RPC / WebSocket で全フェーズを通す。計測と、保存内容の突き合わせが主 | 約2.5分 |
| `load-ui`(画面つき) | 実ブラウザのホスト・管理・参加者3人 + 合成の参加者47人・管理1人。負荷がかかった状態で、実際の画面が最後まで正しく動くか | 約3.5分 |

## 実行方法

ローカル(`dist/cloudflare` が必要なので、先に `npm run build`):

```
npm run build
npm run e2e -- load        # protocol版
npm run e2e -- load-ui     # 画面つき
```

`npm run e2e`(引数なし)は従来どおり `worker-smoke` と `ui` だけを動かす。負荷テストは名前を指定したときだけ動く。

staging(本番相当の Cloudflare 上。**無料枠は本番と共有**なので手動で実行する。CI には入れない):

```
npm run staging:up                # 出力に BASE と E2E_ADMIN_TOKEN が出る
BASE=https://… E2E_ADMIN_TOKEN=… LOAD_REPORT=load-report.json node e2e/load/full-course.mjs
BASE=https://… E2E_ADMIN_TOKEN=… npx playwright test -c e2e/load/playwright.config.ts
npm run staging:down              # 終わったら必ず片付ける
```

テストは自分で参加者(`ld-…`)とセッションを作り、終了時に消す(失敗時も消す)。

### 環境変数

| 変数 | 既定 | 意味 |
|---|---|---|
| `BASE` | `http://127.0.0.1:8821` | 対象の URL |
| `E2E_ADMIN_TOKEN` | ローカル用の既定値 | 管理者のログイントークン |
| `LOAD_PARTICIPANTS` | 50 | 参加者数(protocol版)。100 などに増やすと余裕を見られる |
| `LOAD_POLL_RATIO` | 0.2 | WebSocket を使わずポーリングで動く端末の割合 |
| `LOAD_SEED` | 20261018 | 乱数の種(同じ値なら同じ動き) |
| `LOAD_REPORT` | (なし) | 指定すると JSON のレポートを書く |
| `LOAD_MAX_ANSWER_P95_MS` | 3000 | 回答の応答時間 p95 の上限 |
| `LOAD_MAX_FANOUT_P95_MS` | 5000 | 状態を公開してから WebSocket の端末に届くまでの p95 の上限 |
| `LOAD_MAX_LOGIN_FAILURE_RATE` | 0.05 | 初回のログインが失敗する割合の上限 |
| `LOAD_SYNTHETIC` | 47 | 画面つき版の合成の参加者数 |

## シナリオ(protocol版)

1. **準備**: 参加者50人を作り、セッション・ホスト・管理2台を接続
2. **ログインと入室の殺到**: 前半2割は少しずつ、残りは同時にログイン → 入室 → WebSocket 接続(2割はポーリング)。運営の全端末に参加者数が反映される
3. **イベント開始とエントリー**: 管理端末2台のコマンドがホストに届く。全員が一斉にエントリー(1割は二度押し)。一覧に全員が1件ずつ載る
4. **クイズ5問**
   - 第1問: 出題と同時に全員が答える(最も集中する瞬間)
   - 第2問: 回答がばらけ、6割が1回・2割が2回選び直す
   - 第3問: 締切の直前まで回答が続く。ホストは何もしない(サーバ時刻で自動に締まる)。締切後の試行も混ぜる
   - 第4問: 全員が2秒のあいだに6回ずつ押し直す連打の嵐
   - 第5問: 管理端末2台が途中で手動締切。締切後の試行は受理されない
5. **全員の一斉再接続とホストのリロード**: 切断中にホストが状態を更新 → 全員が一斉に再接続して追いつく。同じ端末の二重接続は 4409。ホストの再接続後も公開を続けられる
6. **ジャックポット3回**: 停止できるのは当選者だけ(他の人は FORBIDDEN)。当選者の停止操作がホストに届く
7. **結果の一斉取得**: 50人が同時に結果を取得(3回)。その間も管理者が書き込み続ける。各自の正誤・順位を、保存した内容と突き合わせる
8. **エンディング → ロビー → セッション終了**: イベントの状態が全員から消える。WebSocket は 4410、ポーリングは終了を検知する

### 確かめていること(抜粋)

- 受付中の回答は全部受理され、締切後の回答は新たに採用されない
- 保存された回答は **1人1件で、各自が最後に受け取った応答と一致**(選択肢も回答時刻も)
- 更新番号 `answerRev` が「採用・置換された回数」とちょうど一致し、運営の3端末に最終の回答数・更新番号が届いて一覧も最新になる
- 状態の公開が全員に届く(WebSocket の端末は p95 でミリ秒〜数百ミリ秒、ポーリングは取得間隔ぶん)
- HTTP 429 / 5xx が 0 件、想定外のエラーが 0 件
- 課金対象リクエストの推定が、無料枠の30%に収まる(1日2回のイベント想定。`quota-budget.ts` と同じ前提)

## 結果の読み方

最後に、各 RPC / WebSocket の所要時間(p50 / p95 / p99 / max, ms)、件数、想定外のエラー一覧、合否が出る。
`fanout-poll:*` はポーリング端末(取得間隔 約3秒)の値で、WebSocket の `fanout:*` とは別に見る。
想定外のエラーが1件でもあれば不合格。

## ローカルの実測(参考。2026-10-18、wrangler dev --local、参加者50)

- 回答の応答 p95: WebSocket 6ms / ポーリング(RPC)36ms
- 状態の公開 → WebSocket 端末: p95 約 260ms(切断からの再接続で追いつく場合を含む。通常は 20ms 前後)
- 結果の一斉取得(50人同時): p95 約 400ms
- ログイン(同時 40 人): p50 約 3.0 秒 / p95 約 3.8 秒
- 全 115 項目 合格、想定外のエラー 0 件

## 既知の限界

- **ログインは直列化される**: ログインのたびに認証用のロックを取り、セッション索引を書き換える(1人あたり約 70ms)。そのため同時ログインの待ち時間は人数に比例する。
  50人が一斉に受付QRを読んでも約4秒で済むが、**100人の同時ログインで p99 が約9秒**になり、ロックの待ち上限(10秒)に近づく。150人超が同時に読むと「Server is busy」になりうる。実際は読み取りが時間的にばらけるので問題になりにくい(`LOAD_PARTICIPANTS=100` で確認できる)。
- **レート制限は1IPあたり 1200回/分**(`PUBLIC_LIMITER`)。このテストは1台から全員分を送るので、本番(参加者それぞれ別の回線)より厳しい条件になる。429 が出たら不合格として数える。
- 無料枠は本番と共有。staging で連続して何度も回すと、その日の枠を使う(1回あたりの推定リクエスト数はレポートに出る)。

## このテストで見つかった問題

- **名簿の同時更新で更新が失われる**: メンバーの追加・更新・削除が排他なしで名簿全体を書き戻しており、同時に操作すると片方が消えた(準備で50人を10件ずつ並列に追加して発覚)。名簿専用のロックで直列化して修正済み。
